# API design

Go back to the [Main README](../../README.md).

## 1. Overview

- Base URL (local): `http://localhost:8080/v1`
- API style: REST, JSON over HTTP
- Framework: Quarkus (Java 21), code in
  [`spectrum-app/src/main/java/edu/ukma/ssdm/teamspectrum/api`](../../spectrum-app/src/main/java/edu/ukma/ssdm/teamspectrum/api)
- Specification: [`openapi.yaml`](openapi.yaml), generated from the code (Code-First)
- Interactive documentation: Swagger UI at `http://localhost:8080/api-docs` locally and on
  [GitHub Pages](https://ukma-fin-ssdm-2026.github.io/Spectrum-project/)
- Authentication: not implemented yet; JWT Bearer tokens are planned
- Versioning: major version in the URL path (`/v1`)
- Data: stub responses from in-memory storage, no database yet

## 2. Resource model

Resources follow the [data model](../architecture/data-model.md).

### Hotel

- Endpoint: `/v1/hotels`
- Description: a property that contains rooms
- Attributes:
    - `hotelId` (UUID): unique identifier, generated by the server
    - `name` (string, 3–40 characters)
    - `address` (object): `city`, `district`, `street` (strings, 3–30 characters),
      `buildingNumber` (integer, 1–100)
- Relations: has many rooms

### Room (models exist, endpoints planned)

- Endpoint: `/v1/hotels/{hotelId}/rooms` (nested, because a room belongs to exactly one
  hotel)
- Description: a bookable unit of a hotel
- Attributes:
    - `roomId` (UUID), `hotelId` (UUID)
    - `roomNumber` (string, 3–40 characters)
    - `roomType` (enum): `SINGLE` | `DOUBLE` | `SUITE`
    - `pricePerNight` (object): `amount` (positive number), `currency` (3-letter code)
    - `roomStatus` (enum): `ACTIVE` | `INACTIVE`
- Relations: belongs to a hotel

## 3. Endpoints

| Method | Path                         | Purpose                 | Success | Errors   | Status      |
|--------|------------------------------|-------------------------|---------|----------|-------------|
| POST   | `/v1/hotels`                 | Create a hotel          | 201     | 400      | Implemented |
| GET    | `/v1/hotels`                 | List hotels (paginated) | 200     | 400      | Implemented |
| GET    | `/v1/hotels/{hotelId}`       | Get one hotel           | 200     | 400, 404 | Implemented |
| POST   | `/v1/hotels/{hotelId}/rooms` | Create a room           | 201     | 400, 404 | Planned     |
| GET    | `/v1/hotels/{hotelId}/rooms` | List rooms of a hotel   | 200     | 400, 404 | Planned     |

## 4. Design decisions

### Why Code-First

- The specification is generated from the annotated code, so it cannot drift from the
  implementation.
- Java types and Bean Validation annotations (`@NotBlank`, `@Size`, `@Min`, `@Max`) become
  schema constraints (`required`, `minLength`, `maximum`) without writing them twice.
- No YAML is maintained by hand: a workflow regenerates `openapi.yaml` on every pull request
  to `main`, and another one publishes `docs/api` to GitHub Pages after the merge.

### HTTP methods and status codes

- `POST` creates a resource and returns `201 Created` with the created object.
- `GET` reads and never changes state; it returns `200 OK`.
- `400 Bad Request` is returned for any input that fails validation.
- `404 Not Found` is returned when the requested hotel does not exist.

### Pagination strategy

- Page-based (offset) pagination: `?page=0&limit=10`. It is the simplest option and allows
  jumping to any page, which fits lists of hotels and rooms of moderate size.
- Defaults: `page = 0`, `limit = 10`. Limits: `page ≥ 0`, `1 ≤ limit ≤ 100`; values outside
  these ranges return `400`.
- The response wraps the items with metadata: `items`, `totalItems`, `totalPages`,
  `currentPage`, `limit`.
- Cursor pagination can replace it later if lists become large, see
  [Quality attributes](quality-attributes.md).

### Validation

- Every request body and query parameter is validated before the handler logic runs.
- Constraints and examples are declared on the models, so they also appear in the
  specification and in Swagger UI.

### Error handling

- Validation errors use one structure for all endpoints: a `fields` array where each item
  has `path` (the invalid field, e.g. `address.city`) and `message` (what is wrong).

```json
{
  "fields": [
    { "path": "name", "message": "size must be between 3 and 40" }
  ]
}
```

- Internal details (stack traces, class names) are never returned to the client.
- Known gaps, planned next: `404` currently has an empty body, and errors have no
  machine-readable `code` or `request_id`. The target is a single error structure for every
  error status.

### Versioning

- The major version is part of the URL path (`/v1/...`). A breaking change will be released
  under `/v2` while `/v1` keeps working during the migration.
- Backward-compatible changes (new optional fields, new endpoints) do not change the version.

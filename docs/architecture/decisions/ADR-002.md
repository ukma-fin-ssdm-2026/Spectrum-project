# ADR-002: Data Storage Strategy (PostgreSQL + Valkey Cache)

**Date:** September 28, 2026  
**Status:** Accepted

## Context
The system (US-001 - US-010) handles structured data with complex relationships: users have roles, hotels contain rooms, and rooms are bound to specific booking dates (FR-001-007, FR-013). At the same time, the system must provide fast response times during client hotel searches and filtering (US-001, US-002) to prevent overloading the database with frequent repetitive queries.

## Decision
**Use PostgreSQL relational database as the primary data store and Valkey in-memory storage as a caching layer.**

All primary data (profiles, permissions, hotel inventory, booking transactions) is stored in PostgreSQL. Filtered hotel and room list queries are cached in Valkey to accelerate read-heavy operations.

## Consequences
*   **Pros:** 
    * PostgreSQL ensures transactional integrity (ACID), which is critical for the booking process to prevent double-booking.
    * Valkey significantly reduces load on PostgreSQL during hotel searches, improving system response time.
*   **Cons:** 
    * Need to maintain two different infrastructure technologies instead of one.
    * Cache invalidation challenge: ensuring Valkey data does not become stale after updates in PostgreSQL (e.g., booking the last available room).
*   **Risks & Mitigation:** 
    * Cache is an ephemeral storage layer. The system must be designed so that if Valkey fails, the backend can continue operating (albeit slower) by fetching data directly from PostgreSQL.

## Considered Alternatives
1.  **NoSQL Database (e.g., MongoDB) as the Single Store:**
    *   *Reason for rejection:* Our system's data (hotels -> rooms -> bookings) is highly relational. NoSQL would complicate maintaining data integrity during booking transactions and require complex backend logic instead of simple SQL JOINs.
2.  **Using PostgreSQL Alone without Caching:**
    *   *Reason for rejection:* Potential system performance degradation under peak loads (e.g., mass hotel searches during high season), as all read operations would directly load the database disk and CPU.

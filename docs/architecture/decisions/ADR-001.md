# ADR-001: Architectural Style Selection (Client-Server with API Gateway)

**Date:** September 28, 2026  
**Status:** Accepted

## Context
The hotel booking system must handle requests from clients (hotel search, room booking) and workers (inventory management, status verification). Functional requirements (FR-008-013, FR-018) require clear role segregation and fast search capabilities. We need to determine how to organize communication between the web client and the backend, considering future scalability under growing load (non-functional requirements).

## Decision
**Use a client-server architecture with Nginx as an API Gateway (Reverse Proxy) in front of the backend services.**

Instead of direct client communication with each individual service, all HTTPS requests pass through the API Gateway, which routes them to the appropriate internal services (Auth Service, HotelRoom Service, Booking Service).

## Consequences
*   **Pros:** 
    * A single entry point simplifies client code (the client is unaware of the internal backend structure).
    * API Gateway allows centralized configuration of SSL termination, CORS, and Rate Limiting.
    * Provides flexibility: we can start as a modular monolith and easily split into full microservices later without client-side changes.
*   **Cons:** 
    * An extra network hop (Nginx) introduces minimal latency (a few milliseconds).
*   **Risks & Mitigation:** 
    * API Gateway is a Single Point of Failure (SPOF). If Nginx goes down, the entire system becomes unavailable. Robust monitoring must be established.

## Considered Alternatives
1.  **Direct Client-Server Architecture without Gateway:** Client communicates directly with each backend service.
    *   *Reason for rejection:* Complicates client-side logic (hardcoding multiple URLs), hinders security configuration, and prevents seamless scalability or future microservice migration.
2.  **Full Microservices Architecture with Service Mesh:**
    *   *Reason for rejection:* Excessive deployment complexity and infrastructure overhead for our current scale of requirements. API Gateway is a sufficient and simpler trade-off.
